# Algorithm Design

Algorithm implementations written while working through algorithm design at
UKM, plus a benchmark that puts the sorting routines head to head.

The sorting files started life as console demos: read `n`, read `n` numbers,
sort, print. To make them measurable I extracted the sorting itself into a
public method (`bubbleSort`, `selection_sort`, `Insertion_Sort`, `heapSort`, and
the existing `quickSort`) and moved all printing into `main`. The algorithms
themselves are unchanged — same loops, same comparisons.

## Sorting benchmark

`benchmark.Benchmark` times each sort on the same random input. Every case is
run once to warm the JIT, then five times, and the **median** is reported — a
single run on a laptop is mostly noise. Each result is also checked for
sortedness, so a fast-but-wrong sort fails instead of scoring well.

Java 17.0.12 · Windows 11 · 32 cores · median of 5 runs · random `int` input

### Quadratic sorts

| Algorithm | 1,000 | 5,000 | 10,000 |
| --- | ---: | ---: | ---: |
| Bubble sort | 0.62 ms | 13.9 ms | 72.1 ms |
| Selection sort | 0.67 ms | 3.9 ms | 14.9 ms |
| Insertion sort | 0.36 ms | 1.5 ms | 4.7 ms |

### O(n log n) sorts

| Algorithm | 10,000 | 100,000 | 1,000,000 |
| --- | ---: | ---: | ---: |
| Quicksort | 1.5 ms | 5.7 ms | 69.1 ms |
| Heap sort | 1.1 ms | 8.6 ms | 95.0 ms |

### What the numbers say

**Growth, not just speed.** Going from 1,000 to 10,000 elements is ten times the
input. Bubble sort goes from 0.62 ms to 72.1 ms — about **116×**. That is the
n² curve showing up in real measurements. Quicksort, over a hundredfold increase
(10,000 → 1,000,000), goes from 1.5 ms to 69.1 ms — about 46×, which is what
n log n looks like when you measure it.

**Equal complexity is not equal performance.** Bubble, selection and insertion
sort are all O(n²), yet at 10,000 elements insertion sort (4.7 ms) is more than
three times faster than selection sort (14.9 ms). Insertion sort walks forward
through memory and stops early on nearly-sorted runs; selection sort always
scans the whole tail. Same asymptotic class, different constant factor — and the
constant factor is what you feel at these sizes.

**Small inputs are not worth optimising.** At 10,000 elements quicksort (1.5 ms)
is only about 3× faster than insertion sort (4.7 ms). Below a few thousand
elements the overhead of recursion and partitioning dominates, which is exactly
why real library sorts switch to insertion sort for small subarrays.

**Quicksort vs heapsort.** Heapsort wins slightly at 10,000 (1.1 vs 1.5 ms) but
loses at 1,000,000 (95.0 vs 69.1 ms). Heapsort's jumps across the array hurt
cache locality once the data no longer fits in cache; quicksort's partitioning
stays local.

### Caveats

These are single-threaded wall-clock numbers from one laptop, with default JVM
settings and no GC tuning. Treat the ratios as meaningful and the absolute
milliseconds as machine-specific.

## Running it

```bash
javac -d out $(find src -name "*.java")     # or just the files you need
java -cp out benchmark.Benchmark
```

The benchmark prints Markdown, so the tables above can be regenerated by
pasting its output.
